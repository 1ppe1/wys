# ベンチマーク（NFR-002）

本言語のコンパイラと生成した実行ファイルの性能を、**絶対値と計測環境だけ**で記録する。ほかの言語や処理系との比較・倍率は書かない（要件定義書 5.1。`scripts/ci.sh` がこの文書と README の倍率の文言を検査する）。値は 1 台の機械での 1 回の計測で、性能の約束（SLO）ではない（SLO は未決。ADR-0029）。

## 1. 計測の方法

| 項目 | 道具 | 内容 |
|---|---|---|
| コンパイルと実行 | `benches/measure.sh` | 各プログラムを `wys build --release`（-O2）でビルドした時間、実行ファイルの大きさ、実行時間（1 回空打ちしてから 10 回の最小値）、最大常駐メモリ、参照カウントの操作の回数（`WYS_RC_STATS=1` で別にビルドして 1 回） |
| `wys check` の規模の伸び | `benches/check_scaling.py` | 1 つの関数の文の数を変えた `wys check` の時間（1 回空打ちしてから 3 回の最小値）。`assign` は代入だけ、`branch` は「レコードを作って `if p.a is not None:` で絞り込む」を繰り返す |
| LSP の遅延 | `benches/lsp_latency.py` | `wys lsp` に同じ全文の `didChange` を 50 回送り、診断が届くまでの時間 |
| AI の評価ケース | `wys eval --format json tests/evals/*/` | 記録の再生で評価ケースを実行したときの成功率と使用量（ネットワークに出ない） |

表は `benches/report.py` で計測の TSV（`benches/results/`、git 管理外）から作る。

**計測環境**: Apple M5 Pro、macOS（Darwin 25.4.0）、コミット `9ff9b54`、Rust 1.99.1、2026-11-11。Linux x86_64 は CI をエミュレーションで回しているため、性能は計測していない。

## 2. コンパイルと実行（release、-O2）

| プログラム | 内容 | コンパイル（ms） | 実行ファイル（バイト） | 実行（ms） | 最大常駐メモリ（KiB） | retain | release |

| `str_build.wys` | 文字列の連結 | 56 | 2,056,376 | 3.7 | 2,144 | 0 | 20,000 |
| `dict_count.wys` | 辞書の追加・更新・読み出し・削除 | 64 | 2,056,376 | 9.4 | 4,960 | 4,000 | 6,002 |
| `py_roundtrip.wys` | Python（`math.gcd`）の呼び出しの往復（FFI、ADR-0018） | 125 | 2,125,152 | 46.2 | 15,680 | 200,002 | 1,000,004 |
| `validate_json.wys` | 約 1 MB の JSON を 100 回 `parse_json` して `validate[list[Row]]` | 86 | 2,056,432 | 1,520.9 | 52,400 | 1,231,800 | 9,951,728 |

※ 最初のプログラムのコンパイルには、clang の初回の起動などが含まれる。

- 実行ファイルはランタイムを静的リンクした単独のファイル（AC-004）。大きさの大半はランタイム。
- 起動の時間は `hello.wys` の実行時間にあたる。
- Python を使うプログラムは CPython 3.14 を埋め込む（ADR-0018）。

## 3. `wys check` の規模の伸び（release）

| 形 | 文の数（`branch` は `if` の数） | `wys check`（ms） |
|---|---:|---:|
| assign | 1,000 | 3.4 |
| assign | 2,000 | 4.6 |
| assign | 4,000 | 8.5 |
| assign | 8,000 | 11.4 |
| assign | 16,000 | 20.1 |
| assign | 100,000 | 114.3 |
| branch | 1,000 | 8.1 |
| branch | 2,000 | 13.3 |
| branch | 4,000 | 25.1 |
| branch | 8,000 | 47.5 |
| branch | 16,000 | 95.5 |

どちらの形も文の数に対して線形に伸びる（#127、#135 で直した。型検査の仕事量が線形であることは単体テスト `flow_analysis_work_is_linear_in_branches` が決定的に検査する）。

## 5. AI の評価ケース（記録の再生）

| ケース | テスト | 結果 | LLM の呼び出し | 入力トークン | 出力トークン |
|---|---|---|---:|---:|---:|
| planner | `test_plan_uses_the_tool` | 合格 | 2 | 30 | 13 |
| planner | `test_budget_stops_the_agent` | 合格（予算で止まる） | 1 | 10 | 5 |
| summary | `test_summary_is_short` | 合格 | 1 | 12 | 2 |

成功率 1.0（3 / 3）。記録はテスト用のプロバイダで作ったもので、実際のモデルの品質を表すものではない。実プロバイダとの往復の遅延と費用は、利用者が `scripts/llm-smoke.sh` で測る（未計測）。

## 6. 計測していないもの

- Web / API のサーバー（NFR-002 の対象。言語に `net` の機能がまだない）
- Linux x86_64 での性能（CI はエミュレーション）
- 実プロバイダでの LLM の遅延と費用

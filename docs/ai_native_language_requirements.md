# AIネイティブ次世代プログラミング言語 要件定義書

> **ステータス:** Draft v0.1（構想・議論用）  
> **作成日:** 2026-11-04  
> **プロジェクト名:** 未定（以下「本言語」）  
> **対象読者:** 言語設計者、コンパイラ開発者、ランタイム開発者、AI/SDK開発者

## 1. 目的とビジョン

Pythonの簡潔な構文、TypeScriptの型表現力、Nimの軽量なネイティブ実行、CodonのPython風コードの高速化、Mojoの所有権・SIMD・アクセラレータ志向を参考に、**人間とAIの双方が安全に開発できる高性能なプログラミング言語**を構築する。

本言語は「既存5言語の完全互換な統合」ではない。各言語の利点を設計原則として取り入れ、相反する要件は明示的な実行境界・段階的な機能拡張によって調整する。

### 1.1 プロダクトゴール

1. Pythonに近い少ない記述量でCLI、バックエンド、データ処理、AIエージェントを実装できる。
2. TypeScriptに近い型推論・Union型・構造的型付けを提供し、コンパイル時に多くのエラーを検出する。
3. CPUネイティブ実行を基本とし、必要な部分だけ明示的に低レベル最適化できる。
4. 既存のPython資産と接続し、後続フェーズでTypeScript/JavaScript環境にも接続する。
5. LLM、ツール呼び出し、エージェント、評価、監査、安全制約を一貫した開発体験として提供する。
6. AIによるコード生成・修正が、コンパイラの機械可読な診断によって検証可能になる。

### 1.2 非ゴール

- すべてのPythonコードを無変更で実行・高速化すること。
- あらゆる処理でC++/Rust/Mojoを超える性能を保証すること。
- TypeScriptの型注釈・npmパッケージを完全互換で直接実行すること。
- 任意のLLM応答について正しさ、決定性、安全性を保証すること。
- 初期版からすべてのCPU、GPU、OS、ブラウザ環境をサポートすること。

## 2. 設計原則

| ID | 原則 | 意図 |
|---|---|---|
| P-01 | Simple by default, explicit when needed | 普段は簡潔に、高性能・危険な操作は明示的に |
| P-02 | Sound boundaries | 動的値、FFI、LLM出力、外部ツールの境界で検証する |
| P-03 | One language, multiple backends | 共通の構文と意味論を、複数の実行ターゲットへ変換する |
| P-04 | Explainable compilation | 型エラー、効果、最適化可否を人間・AIが理解できる形式で返す |
| P-05 | Capability-first security | AIや外部ツールは、許可された能力のみ使用できる |
| P-06 | Incremental interoperability | 互換性は明示的なFFI/ブリッジで拡張し、魔法のような完全互換を約束しない |
| P-07 | Measurable performance | マイクロベンチマークと実アプリ全体の両方で測定する |

## 3. 主要ユースケース

- **UC-01:** 型安全なCLI・APIサーバーを、少ない記述量で開発する。
- **UC-02:** Pythonライブラリを利用しつつ、計算負荷の高い処理をネイティブ化する。
- **UC-03:** 出力型・ツール権限・予算が設定されたAIエージェントを構築する。
- **UC-04:** AIがコンパイラ診断とテスト結果を利用し、コードを生成・修正する。
- **UC-05（後続）:** SIMD/GPUで数値計算・機械学習向け処理を高速化する。
- **UC-06（後続）:** WasmやTypeScript宣言生成を通じ、Web/Node.jsアプリと連携する。

## 4. 機能要件

### 4.1 言語構文・型システム

| ID | 優先度 | 要件 |
|---|---|---|
| LANG-001 | Must | Python風のインデントベース構文、関数、変数、モジュールを提供する。 |
| LANG-002 | Must | ローカル型推論と関数シグネチャでの型宣言を提供する。 |
| LANG-003 | Must | 基本型、コレクション型、レコード型、`T | None`に相当するNull安全性を提供する。 |
| LANG-004 | Must | Union型、Generics、パターンマッチ、網羅性検査を提供する。 |
| LANG-005 | Should | TypeScriptに近い構造的型付けを、公開APIに利用できるようにする。 |
| LANG-006 | Must | 未検証の外部値は`Unknown`相当として扱い、明示的な絞り込み・検証を要求する。 |
| LANG-007 | Must | 型の不一致を静的に検出し、暗黙の安全でない型変換を禁止する。 |
| LANG-008 | Should | `async/await`と、型付きエラー/Result相当の失敗表現を提供する。 |
| LANG-009 | Could | 制約付きメタプログラミングを提供する。任意コードを実行する複雑なマクロは後回しとする。 |

> **注:** 具体的な予約語・型名・構文は言語仕様策定時に確定する。`Unknown`等は概念上の名称。

### 4.2 メモリ管理・並列処理

| ID | 優先度 | 要件 |
|---|---|---|
| MEM-001 | Must | 通常のアプリ開発では、明示的な解放を要求しない安全なメモリ管理を提供する。 |
| MEM-002 | Must | コンパイラ内部で所有権・参照・ライフタイムの一貫したモデルを定義する。 |
| MEM-003 | Should | ARC/ORCに類する参照カウント主体の管理方式を評価し、循環参照への対応を設計する。 |
| MEM-004 | Should | 高性能処理では明示的なBorrow/Move等の最適化手段を提供する。 |
| MEM-005 | Must | use-after-free、二重解放、データ競合に対する保証範囲を仕様で明示する。 |
| MEM-006 | Should | 型安全な並列処理APIを提供し、共有可変状態を制御する。 |

**設計上の制約:** 「GCなし」「完全自動」「所有権チェックなし」「任意の並列処理が安全」を同時に実現する前提にはしない。モデルの統一を優先する。

### 4.3 コンパイラ・実行ターゲット

| ID | 優先度 | 要件 |
|---|---|---|
| COMP-001 | Must | Lexer/Parser、AST、型解析、効果解析、共通IR、コード生成を分離する。 |
| COMP-002 | Must | CPU向けNative実行ファイルの生成を提供する。 |
| COMP-003 | Must | 静的に最適化できない箇所を診断し、意図しない意味変更を行わない。 |
| COMP-004 | Should | LLVMを中心としたNativeバックエンドを採用する。 |
| COMP-005 | Should | Debug/Releaseビルド、最適化レポート、ソース位置付き診断を提供する。 |
| COMP-006 | Could | Wasmバックエンドを追加する。 |
| COMP-007 | Could | MLIRを利用したGPU/SIMD最適化経路を追加する。 |
| COMP-008 | Must | 動的・Native・アクセラレータ間のデータ受け渡しと実行境界を明示する。 |

**方針:** 構文・意味論は共通とし、最初から3系統の実行ランタイムを同時完成させることは目標にしない。

### 4.4 相互運用・パッケージ管理

| ID | 優先度 | 要件 |
|---|---|---|
| INTEROP-001 | Should | CPythonとのFFI/埋め込み呼び出しにより既存Pythonライブラリを利用可能にする。 |
| INTEROP-002 | Should | Python境界で型・例外・所有権・スレッド制約を適切に変換する。 |
| INTEROP-003 | Should | 条件が合う場合、数値バッファの不要なコピーを抑制する。 |
| INTEROP-004 | Should | 依存解決、ロックファイル、再現可能なビルド、パッケージ公開を提供する。 |
| INTEROP-005 | Could | TypeScript型宣言（`.d.ts`）の生成・変換を提供する。 |
| INTEROP-006 | Could | Wasm/JSブリッジでブラウザ・Node.jsから呼び出し可能にする。 |

**制約:** Pythonの動的機能とネイティブコンパイルの完全互換、npmパッケージの無変換直接実行は保証しない。

### 4.5 AIネイティブRuntime・SDK

| ID | 優先度 | 要件 |
|---|---|---|
| AI-001 | Must | 型付きLLMリクエスト/レスポンスAPIを提供する。 |
| AI-002 | Must | LLM出力のスキーマを実行時検証し、不正な出力を明示的に扱う。 |
| AI-003 | Must | エージェントに利用可能なツールと入出力型を宣言できる。 |
| AI-004 | Must | ファイル、ネットワーク、外部サービス等へのアクセスをCapabilityで制限する。 |
| AI-005 | Must | 高リスク操作に対する承認フローをRuntime側で強制できる。 |
| AI-006 | Must | タイムアウト、実行回数、トークン/コスト予算等の制限を設定できる。 |
| AI-007 | Should | モデル呼び出し、ツール実行、使用量、失敗を追跡するトレースを提供する。 |
| AI-008 | Should | モデル応答のモック、記録済み応答の再生、評価ケース管理を提供する。 |
| AI-009 | Should | ネットワーク・ファイル操作等をEffectとして表現し、静的診断とRuntime強制を連携する。 |
| AI-010 | Could | 複数エージェントの連携、分散実行、チェックポイント/再開を提供する。 |

**セキュリティ原則:** LLM出力およびツール戻り値は信頼しない。プロンプト内の指示だけで権限を制御しない。型・Effect解析は有用だが、外部リソースへの権限を保証するにはRuntime側の強制が必要。

**実装方針:** `agent`、`tool`、`llm`等は最初から専用構文に固定せず、まず型付き標準SDK・デコレータ/アノテーションとして実装する。利用実績に応じて言語機能への昇格を検討する。

### 4.6 開発者体験・AIによる開発支援

| ID | 優先度 | 要件 |
|---|---|---|
| DX-001 | Must | `build`、`run`、`check`、`test`、`fmt`相当の統合CLIを提供する。 |
| DX-002 | Must | エラーコード、位置、原因、推奨修正、影響する型・関数を機械可読形式（例：JSON）で出力する。 |
| DX-003 | Should | Language Server Protocol対応、補完、定義ジャンプ、型ホバーを提供する。 |
| DX-004 | Should | `explain`相当の機能で型制約、Effect、最適化できない理由を説明する。 |
| DX-005 | Should | AIが生成したパッチを、型チェックとテストで検証するワークフローを提供する。 |
| DX-006 | Should | Formatter、Linter、ドキュメント生成を公式に提供する。 |
| DX-007 | Could | プロファイルに基づく最適化提案を提供する。自動変更は検証後に適用する。 |

## 5. 非機能要件

| ID | 分類 | 要件・評価方法 |
|---|---|---|
| NFR-001 | 安全性 | 型・所有権・権限に関する保証範囲を明文化し、境界テストを用意する。 |
| NFR-002 | 性能 | 数値計算、文字列処理、Web/API、FFI呼び出し、AIエージェント全体のベンチマークを公開する。 |
| NFR-003 | 可観測性 | 診断、コンパイル時間、実行トレース、外部APIコストを計測できる。 |
| NFR-004 | 再現性 | 依存バージョン、コンパイラバージョン、設定、モデル識別子等を記録できる。LLM出力自体の決定性は保証しない。 |
| NFR-005 | セキュリティ | 最小権限、秘密情報のログ抑制、外部データの非信頼扱い、監査可能な実行記録を原則とする。 |
| NFR-006 | 移植性 | MVPのサポートOS/CPUを明示し、CIで継続検証する。その他の環境は後続対応とする。 |
| NFR-007 | 安定性 | パニック/例外/Resultの扱い、FFI失敗、ツールタイムアウト時の動作を規定する。 |
| NFR-008 | 互換性 | 言語仕様・標準ライブラリ・ABIのバージョニング方針と破壊的変更ルールを持つ。 |

### 5.1 初期ベンチマークの評価軸

- **コンパイル:** コールド/ウォームビルド時間、インクリメンタル更新時間。
- **Native:** 処理時間、最大メモリ、生成バイナリサイズ、起動時間。
- **Interop:** Python呼び出し往復、配列変換、コピーの有無。
- **AIアプリ:** P50/P95レイテンシ、APIコスト、スキーマ検証失敗率、ツール失敗率、評価ケース成功率。
- **DX:** 診断精度、補完応答時間、AIが修正提案を適用した後の型チェック・テスト成功率。

**注意:** 「Python比何倍」の数値目標は、ベースラインとワークロード確定後に設定する。MVP段階で根拠のない一律倍率を約束しない。

## 7. 優先順位とフェーズ

### Phase 1: 言語・ネイティブMVP

- 構文、型推論、Union/Generics、Null安全性、基本モジュール。
- 最小のメモリモデル、AST→IR→CPU Native、基本標準ライブラリ。
- `build`、`run`、`check`、`test`、`fmt`、構造化診断。
- 小さなCLI・計算プログラムの実行。

**完了条件:** 型エラーを事前に検出でき、単独のNative実行ファイルを生成・テストできる。

### Phase 2: AIネイティブMVP

- CPython相互運用の最小機能。
- `async/await`、型付きLLM入出力、Tool API、Capability、承認、予算・タイムアウト。
- Effect解析の基礎、エージェントトレース、モック評価、LSPの初期版。

**完了条件:** 外部ツールを使うエージェントを構築し、出力型エラー・権限拒否・予算超過を検証できる。

### Phase 3: 高性能・広域展開

- SIMD、GPU/MLIR、Wasm、TypeScript型宣言・JSブリッジ。
- 並列計算、プロファイラ、最適化診断、パッケージエコシステム拡充。

**完了条件:** サポート対象の数値処理をCPU/GPU等に明示的に配置でき、実アプリで性能・互換性を比較できる。

## 9. リスクと対策

| リスク | 想定影響 | 対策 |
|---|---|---|
| 高水準の簡潔さとOwnershipの衝突 | 学習コスト・複雑な仕様 | 一貫した内部モデルを先に確立し、高度な操作のみ明示化 |
| Python完全互換への期待 | 非対応機能、性能低下 | FFI境界と対応範囲を公開、互換性テストを設ける |
| 複数バックエンドの同時開発 | 開発遅延 | LLVM Nativeを先行し、GPU/Wasmは後続フェーズ |
| AIツール実行による権限逸脱 | 情報漏えい・破壊的操作 | CapabilityをRuntime強制、承認、ログ抑制、監査 |
| エージェント出力の非決定性 | テスト不安定 | モック/再生、スキーマ検証、評価データセット |
| LLVM/MLIR/CPython連携の保守負荷 | ビルド/ABI問題 | 初期PoCで検証、対象バージョンを固定、CI互換性テスト |
| 新規エコシステムの不足 | 導入障壁 | Python相互運用、公式標準ライブラリ、パッケージ管理を優先 |

## 11. 初期技術検証（PoC）

実装着手時には、以下のスパイクを優先する。

1. **コンパイラPoC:** 最小言語のAST→型チェック→LLVM→ネイティブ実行。
2. **型/所有権PoC:** Nullable Union、Generics、借用、循環参照、並列共有をどう整合させるか。
3. **FFI PoC:** Python関数・配列呼び出し、例外伝搬、データコピー、GILの制約を測定。
4. **AI安全性PoC:** 型付き出力、未許可ツール拒否、承認制御、監査、タイムアウト。
5. **AI開発支援PoC:** JSON診断→AI修正案→型チェック/テストの閉ループ。

## 12. 構文イメージ（非規範的）

以下は利用イメージであり、確定構文・実装済みAPIではない。

```python
type ResearchResult = {
    summary: str
    sources: list[str]
}

@tool(effects=["network"], approval="required")
async def search(query: str) -> list[str]:
    ...

@agent(tools=[search], output=ResearchResult, max_cost_usd=0.50)
async def research(topic: str) -> ResearchResult:
    return await llm.generate[ResearchResult](
        f"Research this topic: {topic}"
    )
```

この例が表す契約は「出力スキーマの実行時検証」「ツール権限と承認のRuntime強制」「費用上限」「失敗の明示的な取り扱い」であり、デコレータ構文自体を必須要件とはしない。

## 13. 次の設計成果物

1. **言語仕様 v0.1:** 文法（EBNF）、型規則、エラー処理、モジュールシステム。
2. **メモリ/Effect ADR:** 安全性の保証範囲と実行時コストを含む意思決定記録。
3. **コンパイラ設計:** AST/IRの構造、診断JSONスキーマ、バックエンド境界。
4. **AI SDK/API仕様:** 型付き入出力、Capability、承認、失敗・監査イベント。
5. **MVPテスト計画:** Conformance tests、セキュリティテスト、ベンチマーク。

**優先判断:** まず「言語の意味論・型・所有権・Effect・FFI境界」を確定する。高性能GPU機能とAI向け糖衣構文は、その土台の上に段階的に構築する。

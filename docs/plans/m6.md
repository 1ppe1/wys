## 方針

- **Effect の推論は「注釈のない関数にだけ」行い、注釈のある関数の意味は変えない（ADR-0024）。** ADR-0014 論点 4 の「注釈のない関数は検査しない」を「注釈のない関数は推論する」に置き換える。推論は型検査の後処理で、関数ごとに記録した呼び出し（`FuncInfo.effect_sites`。`PyObject` のメソッドも含む）の上で、`E(f) = ⋃ E(呼び出し先)`（組み込みは表、注釈のある関数は宣言した集合、注釈のない関数は推論した集合）を不動点まで回す。集合は 4 ビットで単調なので、再帰と相互再帰があっても数回で止まる。モジュールは 1 つの `Module` に併合されているので全体で 1 回でよい。Generic 関数は定義で推論し、単相化したインスタンスは引き継ぐ（ADR-0014 論点 8）。**注釈のある関数の署名は宣言どおり**（推論で広げない。宣言は契約）。これにより E1103（注釈のある関数から注釈のない関数を呼ぶ）は要らなくなり**廃止**する。代わりに、注釈のある `f` が注釈のない `g` を呼び、`g` の推論した集合が `f` の宣言に収まらなければ E1102 を出す。メッセージには「どこで生じた Effect か」を 1 段たどって添える（`g` の中で `print` を呼ぶ位置を `related` に。連鎖が深くても 1 段だけ）。`main` に既定は作らない（ほかの関数と同じく推論する。ADR-0014 論点 7）。`@tool` / `@agent` の `uses` は**必須のまま**（E1403）: ツールの `uses` は LLM に見せる契約であり、ランタイムの Capability の検査の入力なので、推論で黙って広がるのは危うい。この推論が AI-009 の「静的診断と Runtime 強制の連携」の静的側を閉じる: `uses pure` のツールが注釈のない関数を経由して `print` / `py_import` を呼ぶ経路（ADR-0023 論点 11 が実行時の再検査で塞いでいた穴）がコンパイル時に E1102 になる。実行時の入口の再検査はそのまま残す（保証はランタイム）。
- **未使用の Effect は警告 W0203 にする。** 宣言した Effect のうち、本体のどの呼び出しからも要求されないものを警告する（`uses io, exit` で `exit` を呼ばないなど）。`@agent` は `capabilities` に含まれる Effect を除外する（agent はツールを通してその Effect を起こし得る。E1406 の裏返し）。`@tool` は除外しない（過剰な宣言は agent に不要な Capability を要求させるので、むしろ警告したい）。修正案は「名前を外す」か「`uses pure` にする」。エラーのある関数では出さない（W0201 と同じ）。
- **トレースは監査とは別の流れにし、本文は既定で含めない（ADR-0025）。** 監査（`WYS_AUDIT`）は AC-007 の「記録」で、形を安定させて最小に保つ。トレース（`WYS_TRACE=<path>|stderr`）は可観測性（NFR-003）のためで、**スパン**（`agent` / `llm_call` / `tool_call`。開始・終了・親・タスク番号・経過時間・結果）と**イベント**（監査イベントと同じものを同じ流れに写す）を JSON 行で出す。時間 `t_ms` は有効な時計（実時間、`WYS_VIRTUAL_TIME=1` なら仮想時計）で測るので、仮想時計のもとでは出力が決定的になり e2e で比較できる。プログラムからは `llm_usage() -> LlmUsage`（`{llm_calls, tool_calls, input_tokens, output_tokens, cost_usd}`。現在のコンテキストの集計。根なら全体）で読め、Conformance はこれを `print` する。本文（プロンプト・応答・ツールの引数と戻り値）は ADR-0023 論点 16 のとおり既定で含めず、`WYS_TRACE_CONTENT=1` の明示の opt-in で含める。proxy はログを書かない方針も変えない。`wys explain` には足さない（静的な事実だけ。ADR-0022 論点 16）。
- **記録と再生はランタイムに入れ、プロバイダの前後に差し込む（AC-009）。** 記録: `WYS_LLM_RECORD=<path>` を設定すると、どのプロバイダ（モック / `anthropic` / `cmd:`）でも、要求と応答の対を JSON 行で追記する（先頭に `{"kind":"header","v":1,"provider":...}`、以後 `{"kind":"exchange","seq":n,"request":{...},"reply":{...},"latency_ms":n}`）。再生: `WYS_LLM_PROVIDER=replay:<path>` で、子プロセスを起動せずにファイルから順に返す。**照合は「順序＋指紋」**: n 回目の呼び出しは n 回目の記録と対応し、要求の指紋（`model` / `system` / `messages` / `tools` / `schema` / `max_tokens`。`timeout_ms` は時計に依存するので除く）が一致しなければ `Err(kind="replay")`（`message` に何が違うか: `request 3: messages differ`）。記録が尽きても `Err(kind="replay")`。記録した `latency_ms` はモックと同じく待たずに `virtual_ms` を進める（タイムアウトの再生が決定的）。再生中の `llm_mock_push` は実プロバイダと同じく実行時エラー 101。記録には必然的に本文が入る（利用者が名指しで作るファイルなので許容するが、文書に明記し、`wys eval --record` は stderr に一言出す）。API キーは要求に入っていないので記録にも入らない。AC-009 の根拠は「`cmd:` のテスト用プロバイダで記録 → プロバイダなしで再生 → 同じ stdout」の e2e と、`tests/conformance/ai/recordings/` に置いた記録を `replay:` で読む Conformance（harness の `# expect-env:` に `${CASE_DIR}` の展開を足す）。CI は引き続きネットワークに出ない。実プロバイダでの記録は `scripts/llm-smoke.sh --record`（手元だけ）。
- **「評価ケース」は、`wys test` と記録の上に置いた薄い約束にする。** 評価ケース = ディレクトリ `evals/<name>/` に `case.wys`（`test_*` 関数が `llm_generate` / agent を呼び、結果を `assert` する）と `recording.jsonl`。`wys eval <dir>...` は各ケースを `WYS_LLM_PROVIDER=replay:` で `wys test` と同じ経路で実行し、ケースごとの合否と使用量（トレースの集計）をまとめ、`--format json` で `{cases:[{name, passed, failed, llm_calls, tokens, cost_usd}], success_rate}` を出す（要件定義書 5.1 の「評価ケース成功率」）。`wys eval --record <dir>` は設定したプロバイダで実行して記録を書き直す（モデルを替えたときの再評価）。CI は `tests/evals/` の 2〜3 件を再生で回す。採点器（LLM による judge）や期待出力のマニフェストは入れない（判定はテスト関数の `assert`）。
- **費用の上限 `max_cost_usd` は M6 に入れるが、出口条件には含めない。** 価格表は古くなるので proxy の adapter に置き（ADR-0023 論点 13）、応答に任意の `cost_usd` を添える（プロトコル v1 への追加。`cmd:` の作者も添えられる。`usage` にキャッシュの内訳も任意で足す）。ランタイムはコンテキストごとに `f64` で合計し、`@agent(max_cost_usd=float)` を他の予算と同じ順で検査する（`Err(kind="budget")`、監査 `budget_exceeded` の `detail` は `max_cost_usd`）。**閉じる方向**: `max_cost_usd` を設定した agent で応答に `cost_usd` がなければ（未知のモデル、モック、古い `cmd:`）、費用が分からないので予算超過として扱う。モックは費用を返さないので、Conformance では検査せず e2e（`fake_provider.sh` が `cost_usd` を返す）で検査する。
- **LSP は別クレート `wys_lsp` と副コマンド `wys lsp`、同期・stdio、`lsp-server` + `lsp-types`（ADR-0026）。** 初期版の範囲は、診断（`textDocument/publishDiagnostics`。開いているバッファを `frontend_with` の読み込み閉包で重ね、import 先の診断もファイルごとに配る）、型のホバー（式の型・ローカルの宣言型と絞り込み・関数の署名と Effect（宣言 / 推論）・レコードのフィールド。`TypeckResult.expr_types` と `FuncInfo` を使う）、定義ジャンプ（関数・ローカル・型・import 先のファイル）、quickfix（`Hint.replacement` をそのまま code action に）、整形（`format_source`）。補完・リネーム・参照検索は入れない（DX-003 の「補完」は公開準備）。変更のたびにフロントエンドを全部回す（ファイルは小さい。遅延の絶対値を PoC6 で記録し、倍率は書かない）。位置は UTF-8 を交渉し（`positionEncoding`、LSP 3.17）、受け付けないクライアントには UTF-16 に変換する。依存（`lsp-server` / `lsp-types` / `serde`）は `wys_lsp` と `wys_cli` だけで、ランタイムと生成した実行ファイルは変わらない（AC-004）。検査は 3 層: 純粋な関数（`hover_at(fe, pos)` / `definition_at`）の単体テスト、Conformance の `lsp/` に新しいキー `# expect-hover: 行:列 <文字列>` / `# expect-definition: 行:列 -> 行:列`、`wys lsp` を子プロセスにして JSON-RPC を話す e2e（initialize → didOpen → publishDiagnostics → hover → definition → codeAction → formatting → shutdown）。エディタ側の拡張（VS Code）は作らず、汎用クライアントの設定例を `docs/design/lsp.md` に書く。
- **PoC6 は LSP だけ。** Effect 推論・トレース・再生は既存の仕組みの延長で、試作は要らない。LSP はクレートの選択と位置の変換とエディタとの接続に不確実さがあるので、期限 3 営業日のスパイクを先に置く（T9）。
- **正しさの検査は M3〜M5 と同じ 3 つ**（IR の検証器、終了時の生存数、AddressSanitizer）を `ai/trace_*` / `ai/replay_*` にも適用する。トレースと記録はランタイムのヒープ値を作る（`LlmUsage`、記録ファイルの読み込み）ので、生存数 0 を確かめる。性能は「再生 1 回の時間」「LSP の 1 回の診断の時間」の絶対値だけを記録する。
- **持ち越しは早めに、かつ今回で止める。** #87 は T0 で期限付き（1 営業日）に行い、残れば「公開準備」へ送って以後は持ち越し表に載せない。

### PoC6 の判定（T9）

期限は 3 営業日（2026-11-12 まで）。**成功**の基準（すべて満たす）:

1. `wys lsp` が stdio で `initialize` / `initialized` / `didOpen` / `didChange` / `didClose` / `shutdown` / `exit` を扱い、`examples/type_error.wys` を開くと `publishDiagnostics` に E0201 が `code` / `range` / `message` 付きで出る。`import` のあるファイルでは import 先の診断がそのファイルの URI に配られる。
2. ユーザーの手元のエディタ 1 つで 1 が見える（汎用クライアントの設定例を `docs/design/lsp.md` に残す）。
3. JSON-RPC を話す e2e（子プロセス、ネットワークなし）が CI で通る。
4. `cargo tree -p wys_runtime` が変わらない（依存は `wys_lsp` / `wys_cli` だけ。AC-004）。
5. `docs/poc/poc6-results.md` に、1 回の `didChange` → `publishDiagnostics` の時間（`examples/` と `tests/conformance/modules/` の最大のケース）の絶対値、位置の符号化の扱い（UTF-8 を受け付けるクライアントか）、使ったクレートの版を記録した。

**転換**の基準: 3 営業日で 1〜3 のどれかが動かない。次の順で範囲を狭める。

- (a) `lsp-server` / `lsp-types` がツールチェーン（`rust-toolchain.toml` の版、edition 2024、`unsafe_code = deny`）と合わない → `lsp-types` だけ使い、`Content-Length` の枠組みと JSON-RPC の読み書きは手書きにする（小さい）。それも無理なら両方手書き。
- (b) 位置の符号化で詰まる → UTF-8 を受け付けるクライアントだけを対象にし、UTF-16 の変換は T11 へ。
- (c) 1 か 3 が期限内に動かない → LSP を **M6b** に送り、M6a で M6 の出口判定と Phase 2 の出口判定を行う（下の「分割の判断基準」）。
- (d) 2 だけできない（ユーザーのエディタの都合） → e2e を根拠に T10 へ進み、手元の確認は T11 の終わりにまとめる。

## 診断コードの帯

E11xx Effect: **E1103 を廃止**（コンパイラから外す。`error-codes.md` には「廃止（ADR-0024。推論に置き換えた）」と明記して残し、コードは再利用しない）。E1102 は注釈のない呼び出し先にも出るようになり、メッセージに「`g` の推論した Effect `io`（`g` が 12:5 で `print` を呼ぶ）」の 1 段を添え、`related` に呼び出し先の定義と Effect を生む位置を入れる。修正案は従来どおり「`uses` に足す」1 つ。E1101 / E1104 は変えない。**W0203**（W02xx 未使用の警告の帯、ADR-0014 論点 12 の予約）: 宣言したが要求されない Effect。`@agent` は `capabilities` の分を除く。修正案は「名前を外す」か「`uses pure`」。E1402 に `max_cost_usd` の `float` リテラルと負の値を足す。LSP・トレース・再生・評価ケースにコンパイル時の診断は足さない。

## 分割の判断基準

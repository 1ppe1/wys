# ADR-0002: コンパイラ・ツールチェーンの実装言語に Rust を採用する

- **状態:** Proposed
- **日付:** 2026-11-04
- **関連:** 要件定義書 6章（実装言語候補）、COMP-001, COMP-004, INTEROP-001, DX-001, DX-003

## 背景

要件定義書では、コンパイラ本体・解析系・CLIの実装言語の候補として Rust を挙げているが、まだ決定していない。
開発体制は人間1名＋AIエージェント（Claude Code）で、実装は主にAIが担う。そのため、AIが書いたコードを型とテストで機械的に検証しやすいことが重要になる。
将来は LLVM（COMP-004）、CPython（INTEROP-001）、LSP（DX-003）と連携する必要がある。

## 選択肢

### 案A: Rust

- 利点: メモリ安全で、コンパイラ自身のクラッシュや未定義動作を減らせる。LLVM バインディング（inkwell）、CPython 連携（pyo3）、LSP（tower-lsp など）、スナップショットテスト（insta）のライブラリが揃っている。Cargo ワークスペースでクレートを分割しやすい（COMP-001）。学習データが多く、AIが書きやすい。
- 欠点: ビルド時間が長くなりがち。借用規則によって、ASTやIRのグラフ構造（相互参照）の設計に工夫が要る（アリーナとID参照で回避する）。

### 案B: C++

- 利点: LLVM/MLIR を直接使える。
- 欠点: メモリ安全性がなく、AIが生成したコードの検証コストが高い。ビルドシステムとパッケージ管理が煩雑。

### 案C: OCaml / Haskell

- 利点: 型検査器やパーサを書きやすい。
- 欠点: LLVM・CPython 連携やランタイム実装のエコシステムが薄い。ランタイムを別言語で書く必要が出る。

### 案D: Zig

- 利点: C/LLVM との相互運用が容易で、ランタイムも同じ言語で書ける。
- 欠点: 言語仕様が安定版前で、エコシステムと学習データが少ない。

## 決定

（ユーザーレビュー待ち）推奨は案A。上記の利点に加えて、ランタイムも Rust の staticlib として同じ言語で書ける（ADR-0008 で検討）。

## 影響

- ツールチェーンは `rust-toolchain.toml` で 1.99.1 に固定する（NFR-004 再現性）。
- ASTやIRは、アリーナと ID 参照で表現することを設計の前提とする。
- 見直し条件: PoC1 で LLVM 連携にかかる負荷が許容範囲を超えた場合でも、言語自体は変えず、バックエンド方式（ADR-0004）で吸収する。

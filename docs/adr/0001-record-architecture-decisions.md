# ADR-0001: 設計判断をADRで記録する

- **状態:** Accepted
- **日付:** 2026-11-04
- **関連:** 要件定義書「10. 未決定事項」「13. 次の設計成果物」

## 背景

本言語には、型システム、メモリモデル、Effect、FFI境界、Runtime構成など、後から変えにくく互いに影響し合う判断が多い。
要件定義書でも未決定事項はADRに記録すると定めている。
人間だけでなくAIエージェントも設計に関わるので、判断の理由と却下した代替案を後から機械的に追える形で残す必要がある。

## 選択肢

### 案A: 要件定義書に直接追記する

- 利点: 文書が1つで済む。
- 欠点: 判断の経緯や却下した案が残らない。要件定義書が肥大化する。

### 案B: `docs/adr/` に1判断1ファイルのADRを置く

- 利点: 判断ごとに背景・代替案・影響を残せる。履歴を追いやすい。
- 欠点: 一覧の更新が必要になる。

## 決定

案Bを採用する。運用ルールとテンプレートは `docs/adr/README.md` と `docs/adr/template.md` に置く。

## 影響

- 要件定義書「10. 未決定事項」の各項目は、決定時にADRを作成し、ADR一覧の対応表を更新する。
- 要件定義書は「何を満たすか」、ADRは「どう決めたか・なぜか」を扱う役割分担とする。

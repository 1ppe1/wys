# ADR-0007: 構造的型付けと名目的型付けの境界

- **状態:** Proposed
- **日付:** 2026-11-04（同日、設計レビューの指摘を反映して改訂）
- **関連:** 未決定事項 2、LANG-005, LANG-004, ADR-0006, `docs/design/memory-model.md` 2.8

## 背景

LANG-005 は、TypeScript に近い構造的型付けを公開 API で使えるようにすることを求めている。
一方で、ID の取り違え（`UserId` と `OrderId` など）は、名目的な型でしか防げない。
どの型をどちらで扱うかを決める必要がある。

## PoC2 の結果（`crates/wys_typeck/src/experimental/narrowing.rs`）

- 構造的なレコード型では、幅部分型（必要なフィールドを持っていれば互換）を実装できた。
- **構造的なレコード型どうしは `match` で区別できない**ことを確認した。`{x: int}` を要求するパターンは `{x: int, y: int}` にも当てはまるので、2つのレコード型を含む Union を1つのパターンで網羅してしまう。

## 推奨

| 種類 | 型付け | 例 |
|---|---|---|
| `type X = { ... }` のレコード型 | 構造的（幅部分型）。不変 | API の入出力、JSON に対応するデータ |
| `Protocol` 相当のインターフェース | 構造的 | 「`close()` を持つもの」 |
| `class` / `enum` | 名目的 | ドメインモデル、状態 |
| `newtype`（`type UserId = new int` のような構文、構文は未定） | 名目的 | ID、単位付きの数値 |

Union の中で値の種類を区別する方法:
- **MVP（M2）:** `match` の `case` で区別できるのは、プリミティブ型・`None`・名目的な型だけとする（ADR-0006）。**構造的レコードは `case` の対象にできない。** 種類を区別したいデータは `class` か `enum` で定義する。
- **後続（M2 以降に PoC で検証）:** TypeScript の discriminated union のように、リテラル型の判別フィールド（`kind: "circle"` など）による絞り込みを検討する。必要なのは、リテラル型と、`if r.kind == "circle":` を手掛かりにした流れ解析。PoC2 の実験ではまだ検証していない。

レコードのパターン記法（Python の `{...}` はマッピングパターンで、意味が違う）は導入しない。

## 決定

（ユーザーレビュー待ち）上表と、MVP での区別の方法を採用する。

## 影響

- 型検査は、構造的な互換性（フィールドの包含）と名目的な同一性（定義の同一性）の両方を実装する。
- 構造的なレコードを `case` で区別しようとした場合はコンパイルエラーにして、`class` か `enum` を使うよう修正ヒントを出す。
- 幅部分型の実行時表現は `memory-model.md` 2.8 に従う（不変なので、変換の地点で新しい配置にコピーしてよい）。
- `.d.ts` の生成（INTEROP-005）では、構造的なレコードは TypeScript の型エイリアスに、名目的な型はブランド型に対応させる。

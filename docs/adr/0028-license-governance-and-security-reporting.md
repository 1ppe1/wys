# ADR-0028: ライセンス・ガバナンス・貢献・脆弱性報告

- **状態:** Proposed
- **日付:** 2026-11-11
- **関連:** 未決定事項 11（レジストリの運用を除く）、INTEROP-004（前提）、NFR-001、`docs/plans/release.md` T3 / T14、#72、#77

## 背景

リポジトリを公開する前に、ライセンス、著作権者、意思決定の仕組み、貢献の受け入れ方、脆弱性の報告の窓口を決める必要がある。ライセンスのない公開は「全権利留保」になり、利用も貢献もできない。いまの `Cargo.toml` は `license = "UNLICENSED"`、`publish = false`。

制約:

- ランタイム（`wys_runtime`、`wys_runtime_python`）は、利用者のプログラムの実行ファイルに**静的リンク**される（ADR-0008）。ランタイムのライセンスの条件が、利用者のプログラムに及ばないことが望ましい。
- 依存クレート（`ureq` / `rustls` / `serde` / `lsp-server` / `lsp-types` / `jsonschema` など）は、多くが MIT / Apache-2.0。
- 開発は 1 人とAIエージェント。GitHub Actions は使えず、CI はメンテナが手元で回す。
- 本プロジェクトはユーザーの個人作品（2026-11-11 にユーザーが確認）。

パッケージレジストリの運用（未決定事項 11 の後半）は Phase 3 で扱い、この ADR では決めない。

## 選択肢と決定

| 論点 | 決定（推奨） | 主な代替案 | 理由 |
|---|---|---|---|
| 1. ライセンス | **MIT OR Apache-2.0**（利用者が選べる二重ライセンス）。リポジトリ直下に `LICENSE-MIT` と `LICENSE-APACHE`、`Cargo.toml` の `license = "MIT OR Apache-2.0"` | (a) Apache-2.0 単独。(b) MPL-2.0 / AGPL などのコピーレフト | Rust の慣例で、依存と同じ。静的リンクされるランタイムに条件が付かない。(b) はランタイムのリンクに例外条項が要り、採用の障壁になる。2026-11-11 にユーザーが選んだ |
| 2. 著作権者 | ユーザー個人。LICENSE と README の表記は「Copyright (c) 2026 1ppe1」（表記名は 2026-11-11 にユーザーが決めた）。ファイルごとの SPDX ヘッダは付けない | 勤務先 | 個人作品（ユーザーが確認）。履歴の著者メールは公開の直前に noreply に書き換える（`docs/plans/release.md` T16） |
| 3. ガバナンス | 単独のメンテナ + 既存の ADR の手続き。外部の人も ADR を Proposed で提案でき、Accepted にするのはメンテナ | (a) ADR の PR に公開のコメント期間を設ける。(b) 運営委員会 | いまの体制に合う。(b) は時期尚早。外部の貢献者が増えたら (a) を検討する |
| 4. 貢献の権利 | **DCO**（コミットに `Signed-off-by:`） | (a) CLA。(b) なし | 二重ライセンスで受け取るために、貢献者がその条件で提供する意思を記録したい。CLA は手続きが重い |
| 5. 行動規範 | Contributor Covenant 2.1 | 独自に書く | 広く使われ、日本語訳もある |
| 6. 貢献の手順（CONTRIBUTING） | 先に issue。PR は issue に紐づける。テストを先に書く。CI はメンテナが手元で回す（`./scripts/ci.sh`）。ADR のルール。日本語が正、英語の issue も受ける | — | いまの開発のルール（CLAUDE.md）をそのまま外部向けにする |
| 7. 脆弱性の報告の窓口 | **GitHub の private vulnerability reporting を主、メールを従**（メールは勤務先でないアドレス。ユーザーが用意する） | メールだけ | 公開リポジトリなら無料で使え、非公開のやりとりと修正の公表まで GitHub で完結する。有効化はユーザーがリポジトリの設定で行う |
| 8. 報告への対応の約束 | 受領の返答は 7 日以内を目標。修正の期限は約束しない。対象は最新の 0.y だけ（ADR-0029） | 期限を約束する | 1 人の体制で守れる範囲だけを約束する |
| 9. 脆弱性の範囲 | 範囲内: コンパイラ・ランタイム・proxy・LSP。Capability / 承認 / 予算の迂回（AC-007）、秘密情報の漏れ（NFR-005）、メモリ安全性の保証範囲（`docs/design/memory-model.md` §3）の破れ。範囲外: 利用者のプログラムの誤り、Python のコード（ADR-0018: Python はサンドボックスではない）、利用者が指定した `cmd:` のプロバイダ、LLM の出力そのもの | — | 保証している範囲だけを脆弱性として扱う。`docs/security.md`（T11）に詳しく書く |
| 10. 依存のライセンス | `docs/third-party-licenses.md` に `Cargo.lock` の全クレートのライセンスの一覧。配布物にも同梱する | — | 静的リンクする依存の告知（MIT / Apache-2.0 の条件） |

## 影響

- T14 で `LICENSE-MIT` / `LICENSE-APACHE`、`CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`、`SECURITY.md`、`docs/third-party-licenses.md` を作り、`Cargo.toml` の `license` を変える。`scripts/ci.sh` に必須ファイルと `license` の値の検査を足す。
- 著作権者の表記名は `1ppe1`（2026-11-11 にユーザーが決めた）。承認には、従の窓口のメールアドレス（または「メールなし」）の記入が要る。
- 承認したら、ADR 一覧の未決定事項 11 の欄を更新する（レジストリの運用は「Phase 3」と明記）。
- 見直し条件: 外部の貢献者が継続的に増えたとき（ガバナンスとコメント期間）、パッケージレジストリを作るとき。

# ADR-0025: トレース・記録と再生・評価ケース・費用の上限

- **状態:** Accepted
- **日付:** 2026-11-07
- **関連:** AI-006、AI-007、AI-008、AC-009、NFR-003、NFR-005、未決定事項 10、ADR-0022、ADR-0023（論点 2・13・15・16・21 の見直し）、`docs/design/ai-sdk.md` §18〜§21、`docs/plans/m6.md` T4〜T8

## 背景

M5 で AI Runtime の核ができた（ADR-0023）。プロバイダはモック・`anthropic`（`wys llm-proxy`）・`cmd:<path>` の 3 つで、JSON 行のプロトコル v1 でやり取りする。監査イベント（`audit_events()` / `WYS_AUDIT`）は時刻と本文を含めず、Conformance で比較できる。M6 には次が残っている。

- **AI-007（トレース）:** モデル呼び出し・ツール実行・使用量・失敗を追跡する。NFR-003 は「実行トレース、外部 API コストを計測できる」ことを求める。
- **AI-008 / AC-009（記録と再生、評価ケース）:** 外部モデルを呼ばずに、同じテスト入力を再実行できる。M5 のモックは応答をプログラムに書くので、実際のモデルの応答を使ったテストには使えない。
- **AI-006 の残り（費用の上限）:** ADR-0023 論点 13 で、価格表は古くなるので proxy に置き、ランタイムは `usage` だけを数えると決めて M6 に送った。

ADR-0023 論点 16 は、本文（プロンプト・応答・ツールの引数と戻り値）を監査にも既定のトレースにも含めず、トレースの本文は明示の opt-in にすると決めている。論点 21 は、M6 のトレース・再生を入れるときにプロトコル（論点 2）と監査（論点 15）を見直すとしている。

ランタイムの現状（`crates/wys_runtime/src/ai.rs`）: `provider_step` が 1 回の LLM 呼び出しで予算・使用量・監査を扱い、`exchange()` が要求 1 行を書いて応答 1 行を読む。モックの応答の `latency_ms` は待たずに agent の経過時間（`Ctx.virtual_ms`）を進める。使用量は入力と出力を分けて持つ（M6 T0）。`wys test` はテスト関数ごとに別のプロセスで実行する（`WYS_TEST_INDEX`）。

## 選択肢と決定

| 論点 | 決定（推奨） | 主な代替案 | 理由 |
|---|---|---|---|
| 1. トレースの流れ | 監査とは別の流れ **`WYS_TRACE=<path>\|stderr`** にする。JSON 行で、`path` は追記、開けなければ無視（監査と同じ）。監査（`WYS_AUDIT`）の形と意味は変えない | `WYS_AUDIT` に水準を足して 1 本にする | 監査は AC-007 の「記録」で、形を安定させて最小に保ちたい。トレースは可観測性のためで、時刻・入れ子・使用量を持ち、今後も広がる |
| 2. トレースの行 | 2 種類。**スパン** `{"kind":"span","span":n,"parent":n\|null,"task":n,"name":"agent"\|"llm_call"\|"tool_call","agent":str,"tool":str\|null,"start_ms":n,"end_ms":n,"result":str,"usage":{"input_tokens":n,"output_tokens":n}\|null,"cost_usd":x\|null}`。スパンは**終わったときに 1 行**出す。`agent` のスパンは `result` を持たない（`wys_agent_exit()` は本体の `Result` を受け取らない。ABI は変えない）で、`usage` / `cost_usd` は `wys_agent_exit` の時点のその agent の合計（分かった費用の合計。なければ `0.0`）。`llm_call` は `provider_step` の 1 回につき必ず 1 つ出し、`result` は `ok` / `error:<kind>`（呼ぶ前の予算の失敗、`mock_exhausted`、`replay`、`provider` を含む）、応答が届かなければ（呼ぶ前の失敗、輸送の失敗）`usage: null`。`tool_call` はツールの要求 1 つにつき 1 つ出し（拒否されたものも。`tool_calls` の回数とは別）、`result` は `ok` / `tool_error`（ツールが `Err` を返した。agent は続く）/ `refused`（承認の拒否。続く）/ `error:denied` / `error:budget` / `error:timeout` / `error:schema` / `error:approval`。`tool_call` の `parent` は agent のスパン（`llm_call` はツールを実行する前に終わっている）。`spawn` した子は親のスタックを引き継ぐので（ADR-0023 の訂正）、子のスパンの `parent` は、スタックの最内のコンテキストのスパン（`Ctx` にスパンの番号を持つ）。親の agent が先に出ることもあるので「親は子の後に出る」は保証せず、`parent` でたどる。親の agent が出た後に子が使った分は、その agent のスパンには入らない。**イベント** `{"kind":"event","span":n\|null,"t_ms":n,"seq":n,"event":str,"agent":str,"tool":str\|null,"detail":str}`（`event` は監査イベントの `kind`。行の種類の `kind` と区別する。ほかは監査イベントと同じ）。`span` の番号はプロセスの中で 1 から振る。`task` はスケジューラのタスクの番号（`main` は 0。終わったタスクの番号は再利用され得るので、一意ではない） | 開始と終了の 2 行に分ける | 1 行にすれば、読む側が対を組まなくてよい。親が後に出ても `parent` でたどれる。監査イベントを同じ流れに写せば、どのスパンで拒否されたかが分かる |
| 3. トレースの時計 | `start_ms` / `end_ms` / `t_ms` は、有効な時計（`WYS_VIRTUAL_TIME=1` ならスケジューラの仮想時計、それ以外はランタイムの初期化で取る単調時計の起点からの経過）に、**プロセス全体**のモックと再生の `latency_ms` の累計を足したミリ秒。両方のモードで同じ式（agent の経過時間 `Ctx::elapsed_ms` がどちらのモードでも `latency_ms` を足すのと揃える。ADR-0023 論点 14）。プロセス全体の累計のカウンタを新しく持つ。並行するタスクがあると、agent のスパンの長さは agent の経過時間と一致しないことがある | 常に実時間 | 仮想時計のもとではトレースが決定的になり、e2e でファイルを丸ごと比較できる |
| 4. 本文 | 既定では含めない（ADR-0023 論点 16）。**`WYS_TRACE_CONTENT=1`** のときだけ、`llm_call` のスパンに `request`（要求の `system` / `messages` / `schema`）と `reply`（`text` / `tool_calls`）を、`tool_call` のスパンに `args` と `output`（JSON の文字列。スパンの `result` は実行の結果の語彙なので、別の名前にする）を足す。API キーはどの要求にも入っていないので、トレースにも入らない。proxy はログを書かない方針のまま | 本文を既定で含める | NFR-005（秘密情報のログ抑制）。デバッグに要るときだけ明示で開く |
| 5. プログラムからの読み出し | 組み込み **`llm_usage() -> LlmUsage`**（`LlmUsage = {llm_calls: int, tool_calls: int, input_tokens: int, output_tokens: int, cost_usd: float}`）。現在のコンテキストの集計（agent の中ならその agent、根なら全体）。Effect なし（`audit_events()` と同じく、ランタイムの状態を読むだけ）。`cost_usd` は分かった費用の合計（分からない応答は 0 として足す） | スパンの一覧を読む `trace_spans()` | スパンの形は大きく、今後も変わる。Conformance で集計を `print` できれば AI-007 の数え方を検査できる |
| 6. 記録 | **`WYS_LLM_RECORD=<path>`** を設定すると、どのプロバイダ（モック・`anthropic`・`cmd:`・再生）でも、要求と応答の対を JSON 行で書く。最初の LLM 呼び出しでファイルを作り直し（追記しない。別の実行が混ざると再生できない）、先頭に `{"kind":"header","v":1,"provider":"mock"\|"anthropic"\|"cmd"\|"replay"}`、以後 1 回の呼び出しごとに `{"kind":"exchange","seq":n,"request":{要求},"reply":{応答}\|{"error":str},"latency_ms":n}`。`request` はプロトコル v1 の要求（モックのときも同じ形に組み立てる）、`reply` はプロトコル v1 の応答（モックの応答も同じ形に直す。`error` 行と壊れた応答もそのまま）。`latency_ms` はモックなら `MockResponse.latency_ms`、それ以外は実際に待った時間。`reply` は 3 つの形のどれか: (1) プロトコルの応答のオブジェクト（`error` 行と、`parse_reply` が拒む形もそのまま）、(2) JSON の文字列（届いた行が JSON でなかった。再生は同じ `malformed provider response` を返す）、(3) `null` と `"transport": <文言>`（応答が届かなかった。`the provider exited` など。再生は同じ `Err(kind="provider")` を返し、回数は数えない）。モックの `MockToolCall.args_json` が JSON でなければ、`args` に文字列のまま入れる（再生でのツールの引数の検証の文言は変わり得る。割り切り）。開けない・書けないときは `Err(kind="provider", message="cannot write the recording <path>: ...")` で閉じる。ファイルは `0600` で作る（本文が入るため）。プロセスの終わりまでに LLM を呼ばなかったら、ヘッダだけのファイルを作る（評価ケースの記録の欠けと区別する）。`WYS_LLM_RECORD` と `replay:` を同時に使うときは、再生のファイルを全部読んでから記録を開く。正規化したパスが同じなら `Err(kind="provider", message="the recording path is also the replay source")` で閉じる。`wys test` はテストごとに別のプロセスなので、`wys test` に `WYS_LLM_RECORD` を付けると最後のテストの記録だけが残る（評価ケースでは `wys eval --record` を使う） | 追記する。プロバイダの外（`cmd:` の包み）で記録する | 記録はランタイムの側にしか作れない（モックの応答と、プロバイダに関係なく同じ形）。閉じる方向にするのは、記録したつもりで記録されていない状態を作らないため |
| 7. 再生 | **`WYS_LLM_PROVIDER=replay:<path>`**。子プロセスを起動せず、最初の LLM 呼び出しでファイルを読む。n 回目の呼び出しは n 回目の `exchange` に対応し、要求の**指紋**（要求の JSON から `v` と `timeout_ms` を除いたもの。`timeout_ms` は経過時間で変わる。比較は文字列ではなく JSON の値の構造の等価）が一致すれば、記録した応答を返す（`error` 行ならそのまま失敗として扱う）。記録した `latency_ms` は待たずに経過時間を進める（モックと同じ）。再生した応答も回数・トークン・費用を数え、監査を残す（予算の超過も再生される）。再生中の `llm_mock_push` は実行時エラー 101（実プロバイダと同じ） | (a) 指紋をキーにした辞書引き（順序に依存しない）。(b) `wys llm-replay` を `cmd:` のプロバイダとして作る | (a) は同じ要求が 2 回あると区別できない。(b) は再生に `wys` の実行ファイルが要る。順序＋指紋で AC-009（同じテスト入力の再実行）は満たせる |
| 8. 再生の失敗 | `LlmError.kind` に **`replay`** を足す。要求の不一致 `request N: <最初に違う項目> differs`（`model` / `system` / `messages` / `tools` / `schema` / `max_tokens` の順に比べ、`messages` と `tools` は添字まで示す。例: `messages[2].content`、`tools[0].name`）、尽きた `recording exhausted after N exchanges`、読めない・形が違う `cannot read the recording <path>: ...`。失敗の後の呼び出しも同じ失敗を返す。不一致・尽きた・読めないときは、応答が届いていないので `llm_calls` を数えず `llm_called` も残さない | `provider` / `mock_exhausted` を流用する | プログラムの変更で記録が古くなったことを、プロバイダの障害と区別して読めるようにする |
| 9. 再生とツール | 再生はモデルの応答だけを置き換える。**ツールは実際に実行する**（ツールは本言語のコードで、その結果が次の要求に入る。結果が記録と違えば、次の要求の指紋が一致せず `replay` で失敗する）。承認・Capability・予算の検査もそのまま行う | ツールの結果も記録から返す | ツールの実行を飛ばすと、AC-007 / AC-008 の検査を再生で確かめられない。副作用のあるツールは、テストの側で `approval="required"` と `WYS_APPROVAL=deny` などで扱う |
| 10. 記録のプライバシー | 記録には本文が入る（再生に要る）。利用者が名指しで作るファイルなので許容し、文書に明記する。API キーは要求に入らないので記録にも入らない。`wys eval --record` は stderr に「記録には要求と応答の本文が入る」と出す | 本文を伏せて記録する | 伏せると再生できない |
| 11. 評価ケース | 評価ケース = ディレクトリ `evals/<name>/` の `case.wys`（`test_*` 関数が agent や `llm_generate` を呼び、結果を `assert` する）と `recordings/<テスト関数名>.jsonl`（`wys test` はテスト関数ごとに別のプロセスなので、記録もテストごとに分ける）。**`wys eval <dir>...`** は各ケースの各テストを `wys test` と同じ経路で、`WYS_LLM_PROVIDER=replay:<dir>/recordings/<test>.jsonl` と一時ファイルの `WYS_TRACE` を設定して実行し、合否と使用量（トレースの `llm_call` の集計）をまとめる。`--format json` で `{"cases":[{"name","tests":[{"name","passed","llm_calls","input_tokens","output_tokens","cost_usd"}]}],"passed":n,"failed":n,"success_rate":x}`（`success_rate` = 合格したテスト ÷ テストの数。要件定義書 5.1 の評価ケース成功率）。**`wys eval --record <dir>...`** は、環境の `WYS_LLM_PROVIDER`（設定がなければ失敗）で実行し、`WYS_LLM_RECORD` で記録を書き直す。実行の環境は Conformance の harness と同じにする: `WYS_VIRTUAL_TIME=1` を付け（タイムアウトの再生を実時間に依存させない）、開発者のシェルの AI Runtime の変数（`WYS_LLM_*`、`WYS_CAPABILITIES`、`WYS_APPROVAL`、`WYS_AUDIT`、`WYS_TRACE`、`WYS_TRACE_CONTENT`）を外す（`WYS_LLM_MODEL` は要求の `model` に入り指紋を変える）。`--record` は記録のヘッダに使った `WYS_LLM_MODEL` を残し、再生はそれを設定する。一時のトレースは実行の後に消す。終了コードは、すべて合格 0、失敗あり 1、ケースが読めない・記録がない 2。ヘッダだけの記録は「LLM を呼ばない」記録で、テストが LLM を呼べば `replay` で失敗する（1）。テストが 0 件なら `success_rate` は `null`。CI は `tests/evals/` を再生で回す（コミットする記録は `cmd:` のテスト用プロバイダで作ったものだけ）。`docs/plans/m6.md` の T7 の行の形（`recording.jsonl`、`{cases:[{name, passed, failed}]}`）はこの論点で置き換える | (a) 約束とスクリプトだけ（副コマンドなし）。(b) 期待出力のマニフェストと LLM による採点 | 判定はテスト関数の `assert` で足りる。副コマンドにすれば、成功率と使用量を同じ形で出せる。採点器は Phase 3 |
| 12. 費用 | 価格表は **proxy の adapter** に置く（モデル名 → 入力・出力・キャッシュの読み書きの 100 万トークンあたりの USD。`llm_proxy.rs` の定数表）。応答に任意の **`cost_usd`**（数値）を足し、`usage` にも任意の `cache_read_input_tokens` / `cache_creation_input_tokens` を足す（どちらも任意の追加なので、プロトコルの `v` は 1 のまま。`cmd:` の作者も `cost_usd` を返せる）。未知のモデルには `cost_usd` を付けない（日付付きの ID とエイリアスの照合のしかたは proxy の実装で決める）。`error` 行にも `usage` があれば `cost_usd` を付けられる | ランタイムに価格表を置く | 価格表は古くなるので、更新が `wys` の側だけで済む場所に置く（ADR-0023 論点 13）。生成した実行ファイルは価格を知らない |
| 13. 費用の上限 | `@agent(max_cost_usd=float)`（`0.0` は上限なし。負は E1402。`float` のリテラルを E1402 の検査に足す）。ランタイムはコンテキストごとに `f64` で合計し（スタック上のすべての agent に数える）、ほかの予算と同じ場所（呼ぶ前と応答の直後）で検査して `Err(kind="budget")`、監査 `budget_exceeded`（`detail` は `max_cost_usd`）。**閉じる方向**: `max_cost_usd` を設定した agent がスタックにあるとき、応答に `cost_usd` がなければ（未知のモデル、モック、`cost_usd` を返さない `cmd:`）、費用が分からないので超過として扱う（`message` は `max_cost_usd exceeded (cost unknown)`）。この判定は応答の直後にしかできないので、**一度でも費用の分からない応答が来たら、そのスタック上の上限のある agent に印を付け**（`Ctx.cost_unknown`）、以後は呼ぶ前の検査でも同じ `Err` にする（再試行で実プロバイダに課金し続けない）。`error` 行に `usage` があって `cost_usd` がなければ費用は分からないとみなし、`usage` もなければ課金なし（0）とみなす。`cost_usd` が負・NaN・数値でなければ `malformed provider response`。比較は `max_tokens` と同じく「合計 > 上限」で超過。`max_cost_usd=1` のような整数のリテラルも受け付けて `float` にする。デコレータの引数に `float` のリテラルを足すので、AST（`AttrValue`）・型検査の `AgentAttr`・ランタイムの `AgentCfg`（`repr(C)`）とバックエンドの `@.agent.N`・`dump-ir` と `explain-schema.json` の agent の属性も変える。`LlmUsage.cost_usd` と agent のスパンの `cost_usd` は分かった分の合計（なければ `0.0`）、`llm_call` のスパンは分からなければ `null` | 分からない費用は 0 とみなす | 上限を設定したのに守られない状態を作らない。モックでは費用を検査できないので、Conformance ではなく e2e（`cost_usd` を返すテスト用プロバイダ）で検査する |
| 14. 出口条件 | 費用の上限は M6 に入れるが、M6 の出口条件には含めない（`docs/plans/m6.md`）。価格表は手元の `scripts/llm-smoke.sh` で実 API の `usage` と突き合わせる | — | 価格表の正しさは CI で確かめられない |
| 15. 見直し条件 | ストリーミングの応答、ほかの adapter、非ブロッキングの `llm_generate`、並行する agent の順序が変わる再生の需要（論点 7 (a)）、`wys trace` の副コマンド、評価ケースの採点器 | — | — |

## 影響

- 実装は 4 つに分ける（`docs/plans/m6.md`）。
  - **T5:** トレース（スパン、イベント、時計、`WYS_TRACE` / `WYS_TRACE_CONTENT`）と `llm_usage()` / `LlmUsage`。Conformance の `ai/trace_usage_*`、e2e のトレースのファイルの比較
  - **T6:** 記録と再生、`kind="replay"`。Conformance の `ai/replay_*`（`# expect-env: WYS_LLM_PROVIDER=replay:${CASE_DIR}/recordings/x.jsonl`）、e2e の `record_then_replay_reproduces_the_run`（**AC-009 の根拠**）
  - **T7:** `wys eval`、`tests/evals/`
  - **T8:** 価格表、`cost_usd`、`max_cost_usd`
- 生成した実行ファイルの依存は変わらない（AC-004）。トレースと記録はランタイムの中の JSON の読み書きで、`serde_json` は既にある。
- CI はネットワークに出ない（モック・`cmd:` のテスト用プロバイダ・再生だけ）。
- 新しい組み込み: `LlmUsage`、`llm_usage()`。`LlmError.kind` に `replay`。`@agent` に `max_cost_usd`（デコレータの引数に `float` のリテラルを足す。論点 13）。コンパイル時の新しいエラーコードはない（E1402 の範囲が広がるだけ）。
- Conformance の harness と e2e が外す開発者の環境変数に `WYS_TRACE` / `WYS_TRACE_CONTENT` を足す（`WYS_LLM_RECORD` は `WYS_LLM_` の接頭辞で外れる）。

## 訂正（2026-11-07、M6 T6、Fable のレビュー）

- 論点 6: 記録は「最初の LLM 呼び出し」ではなく**プロセスの最初**（ランタイムの初期化）に作り直す。LLM を呼ぶ前に実行時エラーで終わったときに、古い記録が残って再生が通り続けないように。権限の 0600 は、既にあったファイルにも設定し直す。
- 論点 6: `reply` の 3 つの形は JSON の型ではなく項目で区別する（`reply` / `malformed` / `transport`）。型で区別すると、プロバイダが `null` や JSON の文字列を返した行とぶつかる。
- 論点 7: 仮想時計のモード（`WYS_VIRTUAL_TIME=1`）では、実プロバイダを実際に待った時間も agent の経過時間に足す（ADR-0023 論点 14 の「仮想時計では実時間を数えない」の例外）。記録したときと再生したときで、経過時間を同じにするため（`wys eval --record` は仮想時計で動かす）。再生は、失敗の応答でも、応答が届かなかったときも、記録した `latency_ms` を足す（Codex のレビュー）。

## 訂正（2026-11-07、M6 T7、Fable のレビュー）

- 論点 11: `--record` は、プロバイダの設定として `WYS_LLM_PROVIDER` / `WYS_LLM_MODEL` に加えて `WYS_LLM_PROXY`（proxy の場所の上書き）も残す。テストのないケースは 0 件として数え（終了コード 0）、すべてのケースでテストがなければ `success_rate` は `null`。失敗したテストには、`llm_call` のスパンの失敗の結果（`error:replay` など）を添え、`--format json` では出力も `output` に入れる。記録のないテストがあれば、ビルドの前に 2 で終わる。テスト関数のない記録は警告する。

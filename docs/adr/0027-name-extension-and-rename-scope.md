# ADR-0027: 正式名称・拡張子・パッケージ名

- **状態:** Proposed
- **日付:** 2026-11-11
- **関連:** 未決定事項 1、LANG-001、ADR-0010（可視性。未決定事項 1 のうち可視性だけを決めた）、`docs/plans/release.md` T2 / T13、#71

## 背景

未決定事項 1 のうち、可視性の規則は ADR-0010 で決めたが、言語名・拡張子・パッケージ名は「公開前」に決めることにしていた。いまは内部コードネーム `wys` を、CLI の実行ファイル名、拡張子 `.wys`、環境変数の接頭辞 `WYS_`、クレート名 `wys_*`、ランタイムの C ABI シンボル（`wys_list_*` / `wys_rc_*` など）、ランタイムのファイル名（`libwys_runtime.a`）に使っている。用語集は `wys` を「正式な言語名ではない」と明記している。

`wys` を使っている面（2026-11-11 時点）:

| 面 | 量 | 利用者に見えるか |
|---|---|---|
| CLI の実行ファイル名、使い方の文面 | `crates/wys_cli` | 見える |
| 拡張子 `.wys` | 514 ファイル（大半は Conformance） | 見える |
| 環境変数 `WYS_*` | 26 種 | 見える |
| ランタイムのファイル名 `libwys_runtime.a` / `libwys_runtime_python.a` | 配布物の `lib/` | 見える |
| LSP の `source: "wys"` / `serverInfo`、Markdown のコードブロックの言語名 | `crates/wys_lsp` | 見える（エディタ） |
| 文書・例・scripts / benches | docs に約 650 回 | 見える |
| クレート名 `wys_*` | 18 クレート | 見えない（`publish = false`） |
| ランタイムの C ABI シンボル、IR の名前（`@.wys.compiler` など） | ランタイムとバックエンド | 見えない |

名前そのものはユーザーが決める（CLAUDE.md: 勝手に名前を付けない）。

## 選択肢

### 案A: `wys` を正式名称にする

- 利点: 改名の作業がほぼない（内部と外部の名前が最初から一致する）。既存の文書・設定例・配布の仕組みがそのまま使える。改名による回帰の危険がない。
- 欠点: 3 文字の短い名前なので、レジストリや検索で既存のものと重なりやすい（下の衝突の調査）。用語集にある名前の由来の書き方を整理する必要がある。

### 案B: 新名称で一括改名

- 利点: 新しい名前で内部も外部も一致する。
- 欠点: クレート名・ランタイムのシンボル・IR まで変えるので規模が L〜XL。スナップショットの全更新、回帰の危険が最大。

### 案C: 新名称で段階改名（利用者に見える面だけ）

- 利点: 利用者に見える面は新しい名前で一貫する。内部の改名を避けるので規模は M〜L。
- 欠点: 内部名 `wys` が残る（コードを読む貢献者には見える）。

## 決定

**案A を採る: `wys` を正式名称にする**（2026-11-11 にユーザーが決めた）。

1. **名前**: 言語名・CLI のコマンド名・拡張子・パッケージ名をすべて `wys`（小文字の ASCII）にそろえる。拡張子は `.wys`、環境変数の接頭辞は `WYS_`、配布物は `wys-<版>-<target>.tar.gz`、リポジトリは `1ppe1/wys` のまま。文書の中での表記は `wys`（文頭でも小文字）。
2. **改名はしない**: 上の表の面はすべてそのまま。内部名と外部名が一致するので、「内部名」の区別も要らない。
3. **名前の由来**: 用語集の「Winny と Singularity に由来」の記述は、公開する文書から外す（由来は名前の使い方に関係がなく、Winny は日本では特定の事件と結び付いて連想されやすい）。由来を公開するかは、必要になったらユーザーが決める。
4. **文書の表記**: 「本言語」「正式名称は未定」「内部コードネーム（正式名称ではない）」の記述を、承認の後に `wys` に改める（`docs/plans/release.md` の T9 / T13。T13 は改名ではなく、この表記の整理になり規模は S）。要件定義書の「本言語」は要件の文書の呼び方として残してよい。
5. **npm**: `wys` は既に使われている（下の表）。npm に出すとき（Phase 3 の JS 連携）は `wys-lang` などの別名か、スコープ付きの名前にする。

### 衝突の調査（2026-11-11、AI が調べた。商標はユーザーが確認する）

| 対象 | 結果 | 判断 |
|---|---|---|

| PyPI | 未使用 | 問題なし |
| Homebrew（formula / cask） | 未使用 | 問題なし |

## 影響

- 改名の作業（旧 T13 の L）はなくなる。T13 は表記の整理（S）、T9 は README の更新。`scripts/check-names.sh` は不要。
- 承認したら: ADR 一覧の未決定事項 1 の欄を更新し、CLAUDE.md の「言語名・拡張子は未定。勝手に名前を付けない」と「内部コードネーム（正式名称ではない）」、用語集の `wys` と「本言語」の行、利用者向けの文書の「正式名称は未定」を改める。
- 公開の前に: 米国（と、必要なら日本）の商標をユーザーが確認する（`docs/publishing.md` の点検に加える）。
- 見直し条件: 商標の確認で、ソフトウェアの区分に有効な登録があり、使うことに支障があると分かったとき（その場合は案C で名前を選び直す）。

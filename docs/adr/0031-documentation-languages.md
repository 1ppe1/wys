# ADR-0031: 文書の言語（日本語を正とし、利用者向けの入口に英訳を置く）

- **状態:** Proposed
- **日付:** 2026-11-17
- **関連:** ADR-0028（ガバナンス・貢献）、ADR-0029（安定性）、`docs/plans/release.md`（「英語の全訳 → 公開後」）、CLAUDE.md「ドキュメントのルール」、CONTRIBUTING.md

## 背景

0.1.0 を公開した時点で、文書はすべて日本語で、README に英語の要約もない。CLAUDE.md は「文書は日本語で書く」、CONTRIBUTING.md は「文書と議論は日本語が正」としている。

公開後の方針として、ユーザーは「使ってもらう土台」を優先し、英語の読者にも広げると決めた（2026-11-17）。日本語を読めない人は、いまの README からは何の言語かも、入れ方もわからない。

一方で、開発は 1 人と AI エージェントで進めていて、文書は 60 本以上ある（要件定義書、設計、ADR 30 本、計画、仕様）。全部を 2 言語で保つと、片方が古くなる。古い英訳は、ない英訳より害が大きい（とくにセキュリティの保証の範囲）。

決めること:

1. どの文書を英訳するか。
2. 日本語と英語がずれたとき、どちらが正か。
3. GitHub の入口（`README.md`）をどちらの言語にするか。
4. 英訳をどこに置き、ずれをどう見つけるか。

## 選択肢

### 案A: 日本語だけのまま（README に英語の要約を足すだけ）

- 利点: 保守の負担が増えない。
- 欠点: 英語の読者は要約より先に進めない。ユーザーの方針（英語にも広げる）を満たさない。

### 案B: 日本語を正とし、利用者向けの入口だけ英訳する

- 対象: README、入門、AI SDK のガイド、セキュリティ、安定性と互換性。2 巡目にリファレンスと Python との連携。
- ADR・設計・計画・要件定義書・仕様は訳さない。
- 利点: 英語の読者が「何か → 入れる → 動かす → 何が保証されるか」まで読める。訳す量が 600 行ほどで、保てる。
- 欠点: 英語の読者は設計の理由（ADR）を読めない。2 言語のずれを見張る必要がある。

### 案C: 英語を正にして、日本語を訳にする

- 利点: 海外の貢献者にとって自然。
- 欠点: 既存の文書の全訳が要る。ユーザーのレビュー（ADR の承認、出口判定）が母語でなくなり、レビューゲートが弱くなる。

### 案D: 全文書を 2 言語で保つ

- 利点: どちらの読者も全部読める。
- 欠点: 1 人の体制では保てない。

## 決定

**案B を提案する。**

1. **正は日本語。** 英訳と日本語がずれたら日本語が正しい。英訳の先頭にその旨と、元の文書へのリンクを書く。
2. **英訳する文書は次に限る。** 増やすときはこの ADR を置き換える。

   | 英訳 | 元の文書 | 時期 |
   |---|---|---|
   | `README.md` | `README.ja.md` | 1 巡目 |
   | `docs/en/getting-started.md` | `docs/guide/getting-started.md` | 1 巡目 |
   | `docs/en/ai-sdk.md` | `docs/guide/ai-sdk.md` | 1 巡目 |
   | `docs/en/security.md` | `docs/security.md` | 1 巡目 |
   | `docs/en/stability.md` | `docs/stability.md` | 1 巡目 |
   | `docs/en/reference.md` | `docs/guide/reference.md` | 2 巡目 |
   | `docs/en/python.md` | `docs/guide/python.md` | 2 巡目 |

3. **`README.md` は英語にする。** いまの日本語の README は `README.ja.md` に移し、相互にリンクする。GitHub とパッケージの一覧に出るのは `README.md` なので、入口だけは英語を表にする。README は例外として、2 つを同じ PR で更新する（どちらが正かを争わない程度に短く保つ）。
4. **ずれを見つける仕組み。** 英訳の先頭に、訳した時点の元の文書のコミット（短いハッシュ）を書く。`scripts/ci.sh` に、元の文書がそのコミットより後に変わっていたら警告を出す検査を足す（まずは警告だけ。失敗にはしない）。元の文書を変える PR は、同じ PR で英訳も直すか、英訳の先頭に「古い」と書く。
5. **セキュリティと安定性の英訳は、保証の範囲を広げない。** 「保証すること・しないこと」を 1 対 1 で訳し、要約や言い換えで強い主張にしない。
6. **用語。** `docs/glossary.md` に英語の対訳の列を足し、英訳はそれに揃える。
7. **そのほかは変えない。** ADR・設計・計画・要件定義書・仕様、コードのコメント、コミットのメッセージの方針は今のまま。issue と PR は日本語でも英語でもよい（CONTRIBUTING.md のとおり）。エラーメッセージの言語はこの ADR の範囲外。

## 影響

- 英語の読者が、インストールから agent の例まで英語だけで進める。
- 利用者向けの 5 本（後に 7 本）を変えるたびに、英訳の更新が要る。
- 更新が必要な文書: CLAUDE.md「ドキュメントのルール」（「文書は日本語で書く。英訳は ADR-0031 の対象だけ」）、CONTRIBUTING.md（言語の説明）、`docs/README.md`（索引）、`docs/glossary.md`（対訳の列）、`scripts/ci.sh`（ずれの警告）。
- 公開する文書の制約は英訳にも及ぶ: 名前の由来を書かない、根拠のない性能の倍率を書かない。
- 見直す条件: 英語の貢献者が設計の文書を必要とするようになったとき（ADR の要約の英訳を検討する）。英訳のずれが続いて保てないとき（対象を減らす）。

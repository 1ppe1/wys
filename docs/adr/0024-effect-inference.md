# ADR-0024: Effect の推論（注釈のない関数だけを推論する）

- **状態:** Proposed
- **日付:** 2026-11-07
- **関連:** AI-009、AI-004、DX-004、未決定事項 5、ADR-0014（論点 4・5・7・10・12 を置き換える）、ADR-0017、ADR-0018 論点 9、ADR-0022 論点 11〜14、ADR-0023 論点 7・11、`docs/plans/m6.md` T1〜T3

## 背景

ADR-0014 は Phase 1 の Effect を「注釈だけ」にした。注釈のない関数は検査も推論もしない（論点 4）。注釈のある関数から注釈のない関数を呼ぶと E1103 にして、「注釈は呼び出し木の葉から付ける」運用を促した（論点 5）。推論・未使用の Effect の警告・`main` の既定は M6 で決めるとした（論点 7・12、見直し条件）。

M5 で Effect は AI Runtime の入力になった。

- `@tool` / `@agent` の関数は `uses` が必須（E1403）。
- ツールの `uses` は agent の `capabilities` に含まれなければならない（E1405）。
- ランタイムはツールの宣言した Effect を Capability と突き合わせ、`wys_py_*` / `wys_exit` / `wys_llm_*` の入口でも再検査する（ADR-0023 論点 11）。

いまの規則には穴と不便がある。

- 注釈のない関数は E1103 で呼べないので、`@tool` の本体から普通の補助関数を呼ぶには、その補助関数と、それが呼ぶすべての関数に `uses` を付けなければならない。AI が生成する Python 風のコードではこれが重い。
- 注釈のない関数を経由した Effect は、コンパイル時には見えない。実行時の入口の再検査で止まるが、AI-009 の「静的診断と Runtime 強制の連携」の静的側が閉じていない。
- `wys explain` の `required` は推論ではない（注釈のない呼び出し先の分を含まない）。

いまの実装は、型検査が関数の本体を検査しながら呼び出しを `FuncInfo.effect_sites` に記録する（`EffectSite { callee, span, effects }`。注釈のない呼び出し先は `effects = None`）。E1102 / E1103 も本体の検査中にその場で出し、関数の中のすべての E1102 に「足りない Effect の和集合」を 1 つの修正案として後から付ける（どの E1102 の修正を適用しても 1 回で全部消える）。`PyObject` のメソッドの呼び出しも、型検査の後なので `python` として拾える。モジュールは `wys_resolve::load_program` が 1 つの `Module` に併合する。

## 選択肢と決定

| 論点 | 決定（推奨） | 主な代替案 | 理由 |
|---|---|---|---|
| 1. 推論の対象 | **注釈のない関数だけを推論する。** 注釈のある関数の Effect は宣言した集合で、推論で広げも狭めもしない（宣言は契約） | (a) 推論せず警告だけ出す。(b) 注釈がなければ純粋とみなす（Koka） | (a) は AI-009 の静的側が閉じない。(b) は既存のケースと AI が生成するコードの大半を壊す（ADR-0014 論点 4 の理由のまま）。宣言を推論で書き換えると、ツールの `uses`（LLM に見せる契約、Capability の検査の入力）が黙って変わる |
| 2. 推論の規則 | 関数 `f` の推論した集合 `E(f)` は、本体の呼び出しの Effect の和集合。呼び出し先が組み込み関数なら表の集合（ADR-0014 論点 6、`python` / `llm` の組み込みを含む）、`PyObject` のメソッドなら `python`、注釈のある関数なら宣言した集合、注釈のない関数なら `E(呼び出し先)`。メソッド（`append` / `get` / `pop`）、演算子、`?`、`match` は Effect を持たない（ADR-0014 論点 5 のまま） | — | ADR-0014 の検査と同じ表を使うので、推論と検査が食い違わない |
| 3. 推論の位置と方法 | 型検査の**後処理**。すべての関数の本体を検査した後に、`effect_sites` の上で不動点を回す（すべての注釈のない関数を空集合から始め、変化がなくなるまで和を取る）。集合は 4 ビットで単調に増えるだけなので、再帰・相互再帰があっても止まる。モジュールは併合済みなので全体で 1 回。**E1102 もすべて後処理で出す**: 本体の検査は `effect_sites` の記録だけにし、不動点の後で、注釈のある関数ごとに `sites` を位置の順に見て E1102 を作る（注釈のある呼び出し先も、ない呼び出し先も）。作った診断は W0201 と同じく、その関数の診断の範囲に位置の順で差し込む（Conformance の `# expect-error` は出た順で突き合わせるので、順序を決定的に保つ）。順序は「推論 → E1102（と修正案の統合）→ W0201 / W0203 の抑止の判定」。`uses` 節に E1101 がある関数では E1102 を出さない、という現行の条件も引き継ぐ | 構文の走査で前処理する | 前処理では `PyObject` のメソッドの呼び出しが見分けられない（型が要る）。後処理なら、本体の検査中に記録した呼び出しをそのまま使える |
| 4. Generics | Generic 関数は定義で 1 回推論し、単相化したインスタンスはその集合を引き継ぐ（ADR-0014 論点 8 と同じ） | インスタンスごとに推論する | 型引数は Effect に影響しない（関数値がないので Effect 多相がない） |
| 5. 注釈のある関数の検査（E1102 の拡張） | 注釈のある `f`（宣言 `D`）が呼ぶ `g` について、`g` が注釈のない関数なら `E(g)` が `D` に含まれるかを検査し、含まれなければ **E1102**。メッセージには、どこで生じた Effect かを 1 段だけ添える（例: ``g` has inferred effect `io` (it calls `print` at 12:5)`）。`related` には、`g` の定義（`kind: "function"`）に続けて、足りない Effect ごとに（`io` / `exit` / `python` / `llm` の順で）それを生む `g` の中の最初の呼び出しを 1 件ずつ入れる（`kind: "function"`、`name` は呼び出し先、`span` は呼び出しの位置。診断のスキーマは変えない）。修正案は従来どおり 1 つで、関数の中のすべての E1102（注釈のある呼び出し先と、ない呼び出し先の両方）の足りない Effect の和集合を `f` の `uses` に足す。自己再帰は従来どおり通す | 連鎖をすべてたどって表示する | 1 段あれば、`g` を開けばさらに次が分かる（`wys explain` で `g` の `sites` も読める）。連鎖の全体は長く、診断 JSON が大きくなる |
| 6. E1103 | **廃止する。** コンパイラは E1103 を出さない。`docs/spec/error-codes.md` では、既存の廃止（E0405、E0007）と同じく表から外し、末尾の「廃止:」の段落に「E1103（`uses` を書いた関数から `uses` のない関数を呼んでいる。ADR-0024 で推論に置き換えたため廃止）」を足す。コードは再利用しない。`every_error_code_has_a_case` は表の行だけを読むので変えない。`wys explain E1103` は未知のコードになる（E0405 と同じ）。Conformance の `types/E1103_calls_unannotated.wys` は、同じプログラムが通ることを確かめるケース（推論した Effect が宣言に収まる）と、E1102 になるケースに置き換える | 警告に格下げする | 推論があれば、注釈のない関数を呼んでも `uses` が閉じる（論点 5）。制約を緩める変更なので、いま通るプログラムはすべて通る |
| 7. 未使用の Effect（W0203） | 注釈のある関数で、宣言した Effect のうち本体のどの呼び出しからも要求されないもの（`D − (要求の和集合)`。注釈のない呼び出し先は推論した集合で数える。**自分自身への呼び出しは和集合から除く**。除かないと、自己再帰する関数では宣言がすべて「使われた」ことになる。注釈のある関数どうしの相互再帰は、宣言を契約として見逃す）を **W0203** で警告する。`@agent` の関数は `capabilities`（省略したときの既定の `io, llm` を含む）に含まれる Effect を除外する（agent はツールを通してその Effect を起こし得る。E1406 の裏返し）。`@tool` は除外しない。修正案は、使われない名前を外す修正（すべてが使われなければ `uses pure`）。エラーのある関数では出さない（W0201 と同じ） | (a) `@tool` も除外する。(b) 警告を入れない | 過剰な `uses` のツールは、agent に不要な Capability を要求させる（E1405）。最小権限に向けて警告したい。W02xx は未使用の警告の帯（ADR-0014 論点 12 の予約） |
| 8. `@tool` / `@agent` の `uses` | **必須のまま**（E1403） | 省略を許し、推論で補う | ツールの `uses` は LLM に見せる契約で、ランタイムの Capability の検査の入力（ADR-0022 論点 11・14、ADR-0023 論点 7）。推論で補うと、補助関数の変更でツールの権限が黙って広がる |
| 9. `main` / `test_*` | 既定を作らない。注釈がなければほかの関数と同じく推論する | `main` の既定を `io, exit` にする | 推論があれば既定は要らない。既定を作ると「注釈がない関数は推論する」の例外になる |
| 10. IR と `dump-ir` | `Function.effects` に、注釈があれば宣言した集合、なければ推論した集合を入れ、`Function.effects_inferred: bool` で区別する。lowering が合成する関数（ツールのトランポリン、`wys test` の入口）は `None` のまま（`effects_inferred = false`）。Generic のインスタンスは、lowering がいまと同じく定義の値（`宣言 ∨ 推論`）を写す。`dump-ir` は注釈なら `uses io`、推論なら `uses(inferred) io`（空なら `uses(inferred) pure`）。注釈のない関数の `dump-ir` の行はすべて変わる。バックエンドは `Function.effects` をツール表の Effect のビットに使うが、`@tool` は `uses` が必須（E1403）なので、ツール表に入る関数の値は常に宣言した集合で、生成コードは変わらない | 推論した集合を IR に入れない | ADR-0014 論点 9 の「後続のパスが使える属性」に合わせる。M6 の LSP のホバーもこの値を使う |
| 11. `wys explain` | `function.effects` に `inferred` を足す。注釈がなければ（`declared` が `null`）推論した集合の配列で `required` に等しく、注釈があれば `null`。`required` は本体の呼び出しの Effect の和集合で、注釈のない呼び出し先は推論した集合で数え、自分自身への呼び出しは除く（注釈のある関数では `declared − required` が W0203 の対象と一致する）。`sites[].effects` は注釈のない呼び出し先でも推論した集合で埋める（いまは空。ADR-0014 論点 10 が予告した**意味の変更**）。`annotated` は残す。版は上げない（ADR-0017 論点 1。項目の追加と、予告した意味の変更）。`explain-schema.json` の説明と、explain のスナップショット（`inferred` の追加ですべて）を更新する | — | ADR-0014 論点 10 の「M6 で推論が入ったら `required` が推論結果になる」のとおり |
| 12. AI-009 と Runtime | 推論で、注釈のない関数を経由した Effect もコンパイル時に検査できる（`uses pure` のツールが補助関数を通して `print` / `py_import` を呼ぶと E1102）。**実行時の入口の再検査は残す**（ADR-0023 論点 11）。保証は Runtime が担い、静的な検査は早期発見のため | 静的に閉じたので実行時の再検査をやめる | セキュリティ原則（Runtime 強制が前提）。静的な検査は、未来のコンパイラの誤りや FFI の経路を塞がない |
| 13. 見送るもの | Effect 多相と関数値、利用者定義の Effect、階層的な名前、`fs` / `net`（対象の組み込みがない） | — | 関数値（E0213）が入るまで要らない。`fs` / `net` は名前を足すだけ |

## 影響

- 実装は 2 つに分ける（`docs/plans/m6.md`）。
  - **T2:** 推論（不動点）、E1102 の拡張、E1103 の廃止、IR・`dump-ir`・`wys explain`・スキーマ、Conformance（`types/E1102_inferred_*`、`explain/effects_inferred`）、`wys_typeck` の単体テスト（相互再帰、モジュール越し、Generic）
  - **T3:** W0203 と Conformance（`types/W0203_*`）
- 互換性: いまエラーなく通るプログラムは、エラーなく通る（制約を緩める変更。いまは E1103 のため、注釈のある関数が呼べるのは組み込み関数と注釈のある関数だけなので、推論で新しい E1102 は生じない）。E1103 になっていたプログラムは、推論した集合が宣言に収まれば通り、収まらなければ E1102 になる。W0203 の警告は新たに出る。CLI の終了コードは変わらないが、Conformance は警告も過不足なく突き合わせるので、既存の 3 ケースに `# expect-warning: W0203` を足す: `ai/agent_capability_denied.wys` の `run_py`（実行時の `tool_denied` を見るための故意に広い宣言なので、警告が出るのが正しい）、`lang/effects_annotated_program.wys` の `report`（`exit` を使わない）、`types/E1405_tool_effect_not_granted.wys` の `run`。生成コードは変わらない。
- 更新する文書: `docs/spec/error-codes.md`（E1102 の説明、E1103 の廃止、W0203）、`explain-schema.json`、`docs/design/ir.md`（`effects_inferred` と `uses(inferred)`、バックエンドがツール表に使うこと）、`docs/design/ai-sdk.md`（AI-009 の静的側）、用語集（Effect、`uses` 節の「書かない関数は検査しない」、推論した Effect）、`docs/README.md`（成果物 2 の Effect の欄）、`docs/roadmap.md`、`docs/test-plan.md`（「推論は M6」の記述）、`wys_typeck` のコメント（「注釈がなければ検査しない」）、ADR 一覧と未決定事項 5 の欄。ADR-0014 は Accepted なので書き換えず、ADR 一覧の 0014 の行の状態を「Accepted（論点 4・5・7・10・12 は ADR-0024 で置き換え）」にする。
- 見直し条件:
  - 関数値を入れるとき（Effect 多相、高階関数の推論）
  - 利用者定義の Effect か、`fs` / `net` の組み込みを入れるとき
  - 推論の時間が大きなプログラムで問題になったとき（いまは関数の数と呼び出しの数に比例する回数で止まる）
